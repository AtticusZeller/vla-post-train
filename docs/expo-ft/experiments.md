## 2026-10-18 · 固定种子上的联合更新：15k 与约 7k 基座都拉到 90% 以上

单一场景：`beat_block_hammer` Easy、`ROBOTWIN_FIXED_SEED=1`（训练种子段 100 的第一个有效种子 10100000，每回合同一场景与
指令）。参考实现的方法与默认超参（N=K=8、UTD 20、每回合 3 次 update、10 回合后开始更新），β=0.05（用户 2026-10-16 定），
`02-xense-training`。代码为 expo-ft `77cb999` 加 `rl_joint.sh` 的 `PORT`/`N_EDIT` 参数（之后提交在 `2be2105`；那时还没有单次尝试判定，用的是官方协议）。两次运行 00:10 同时启动，
写这一节时（10:20）仍在跑。成功率是在线训练回合（完整 EXPO 策略：critic 在 8 个基座候选与 8 个编辑候选中选），
不是单独的评测。

3 h 转正，10 h 时 0.24（最大 0.57）；update 选中编辑候选的比例从 0.98 降到约 0.65；π₀.₅ 参数范数 1804.590→1804.63；
编辑网络熵 −259、温度 1.00→1.25 仍在上升。

### 2 结果分析

- **方法在单一场景上复现出来了。** 两个基座更新前分别是 6/10 与 1/10，更新后都升到 90% 以上：72% 基座最近 50 回合
  49/50，31% 基座 46/50。成功回合也更短（120→80 步、164→105 步）。用户结论（2026-10-18）：“RoboTwin 单任务上跑通
  EXPO-FT” Task 完成，代码通过，原算法有效。
- **较弱的基座也能拉上去，只是慢一些。** 约 7k 基座在 4–4.5 h（约 100 回合）达到 90%，15k 基座 3 h 左右首次达到，
  约 7 h（300 回合）后才稳定在 95% 以上。
- **critic 按预期收敛。** Q 的初值偏负、随更新单调回升；critic loss 很早就降到 1e-3，成功率的上升与 Q 转正的时间大致
  对应。Agent 推断：初值偏负来自 REDQ 取 2 个头的最小值，悲观偏差经折扣回溯（γ⁸≈0.92）累积。
- **π₀.₅ 参数变化很小。** 每次 update 只有 1 步 π₀.₅ BC，500 回合后参数范数只变 0.04。
  - Agent 推断：提升主要来自 critic 在候选中挑选，单独评测 RL 后的 π₀.₅ 会接近基座。未验证。
  - 用户判断：LoRA 更新仍是必要的（原文消融里不训 LoRA 成功率上不去）；这次变化小，大概率因为场景固定、没有随机性。
    若回灌到 π₀.₅ 的部分没有意义，策略就没有真正从经验中学习，更像是 π₀.₅ 去适应编辑策略、只给出大致轨迹，最后的
    成功率交给小的编辑策略。是否单独评测 π₀.₅ 留到消融或研究“吸收了多少”时再做。
- **编辑网络停在最大熵。** β=0.05、112 维时熵的上限是 112·ln 0.1 ≈ −258，默认目标 −56 达不到，温度一直上涨，熵项
  （约 300）远大于 Q（约 0.2）。Agent 推断：编辑实际上是 ±0.05 内的均匀扰动；`adjust_target_entropy=True` 会把目标改成
  −56 + 112·ln 0.05 ≈ −391。用户决定（2026-10-18）：debug 阶段超参不变，评估超参时再看。
- **证据边界。** 只有一个种子、一个任务；成功率来自训练回合，没有在评测种子段上测；每个基座只有一次运行。
- **工程。** agent checkpoint 每 2000 步存一份、每份 16 GB，参考实现最多保留 100 份，两次运行约 75 GB/h；夜里每小时
  手动删到每次运行只剩最新两份，之后 `rl_joint.sh` 改为 `--max_to_keep=2`。

### 3 下一步

- 用户 2026-10-18 定：先提训练效率。用户判断主要慢在仿真，打算迁移 RLinf 接 RoboTwin 的做法（场景复用、多环境并行，
  或直接用其分支），也考虑 RLinf 的 ManiSkill3；训练与平时评测改用单次尝试判定（第一次没成功即失败，不考虑
  recovery），论文的完整评测再用官方协议。效率提上去后再恢复场景随机性。

## 2026-10-16 · 联合更新的显存布局与仿真采样耗时（白天诊断）

工程 smoke，不作算法结论。15k 基座、β=0.05、全新启动、训练种子段 100（每回合换种子），5 张卡（GPU 0 推理与环境端，
GPU 1–4 更新），`XLA_PYTHON_CLIENT_PREALLOCATE=false` 以便 `nvidia-smi` 显示实际用量。代码为 expo-ft `bbd07c2` 加工作区改动，后提交为 `e0b363b`
（见 [log.md](log.md)）。

### 1 原始记录

#### 各卡显存峰值

|---|---|---|---|---|
| `smoke_layout_split` | 只拆卡 | 72.9 GB（更新前 23.7 GB） | 各 68.4 GB | 第一轮 150–190 s/次，第二轮 7.4 s/次，无 OOM |
| `smoke_layout_split2` | 拆卡 + CPU 取 batch | 39.6 GB（更新前 23.2 GB） | 各 68.4 GB | 3 轮，第一轮约 44 s/次，之后 7.4 s/次，无 OOM |

### 2 结果分析

- **GPU 0 的 OOM 有两个来源。** 一是它兼做数据并行的一份训练分片；二是预取的 update batch 落在默认设备上，约 45 GB。
  两者都去掉后 GPU 0 剩约 40 GB 余量。余下的 39.6 GB 里还有每轮更新后复制过来的整份训练状态（含推理用不到的优化器
  状态），可以再省，未做。
- **采样慢在环境侧，不在模型推理。** 失败回合 400 步约 180 s，成功回合 100–160 步约 45–70 s，换种子时每回合再加约 60 s
  reset（官方协议先让脚本专家跑一遍）。update 只在回合结束时做，约 22 s，GPU 大部分时间在等环境。
- [ ] **未验证**：循环里取观测与环境动作比单独计时合计多约 180 ms，疑似 websocket 传输或序列化开销。
- 渲染降到 8 spp 能省约 140 ms/步，但用户判断渲染不是主要问题，不改，以免与示教数据的画面不一致。

## 2026-10-16 · RoboTwin `beat_block_hammer` 夜间 SFT 基座与联合更新调试

单任务、单种子段、Easy（demo_clean），50 条示教。代码为 expo-ft `robotwin-sim` 夜里逐步修到 `bbd07c2`、

#### SFT 基座：训练步数与成功率

配置 `pi05_robotwin_beat_block_hammer_lora`（LoRA，H=16，batch 64，恒定 2.5e-5），只评最后一个 checkpoint，
`--only_base_actions`，每个分片一个种子段（从 100000 起）。

`fj3wpdek` 更新后的数值都有限：critic loss 0.0025，Q 均值 −0.94（−1.27～−0.53），actor 已更新 29 步、参数范数
1804.586→1804.592，`edit_actor_loss` 106。环境每步约 0.6–1 s（含推理），一回合最长 400 步；首次 update 编译约
150–210 s，之后每次约 7 s。

### 2 结果分析

- **训练步数决定基座强弱。** 4k、约 7k、15k 依次是 14%、31%（32 回合）、72%；4k 时 loss 已降到 0.0014，loss 曲线
  不能代替成功率选步数。约 7k 落在 30% 下沿，40% 左右的基座大概需要 1 万步附近。
- **编辑动作是联合更新成功率塌陷的直接原因。** 同一批种子上，不加编辑 8/10，加 β=0.2 的编辑 0/5；RL 更新开始后
  0/10。推断：edit actor 逐步、逐维独立地在归一化关节增量上加最多 β 的偏移，β=0.2 约对应每步 ±0.1–0.15 rad
  的目标抖动；critic 未训练时约一半动作块会选中编辑过的候选，精细抓取被破坏。β=0.05 时完整策略 4/10，仍低于
  无编辑的 8/10。
- [ ] **未验证**：β=0.05 下更新能否把成功率拉回基座以上。只有更新后 2 回合，样本不足。
- **显存布局是 RL 的工程瓶颈。** GPU 0 同时放一份数据并行的训练分片和推理用参数副本；`MEM_FRACTION=0.95` 时恢复运行
  撑过了多轮 update，全新启动在第一轮就 OOM（缺约 1 GB）。
