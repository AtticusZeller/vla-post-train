## 2026-10-18 · 环境吞吐与异步多环境短跑：一卡一个环境线性扩展

工程验证，`xense-training-h100`，`beat_block_hammer` demo_clean、固定种子 10100000、单次尝试判定。环境端为 expo-ft
`3fbdd2d`（复用 task 对象），learner 为 `f85fc6a` 前的工作树（smoke，W&B `l0zhamis`，目录已删）。

### 1 原始记录

只跑环境端，每个环境 reset 后原地保持 30 步，计 `step`（act）与 `get_observation`+`get_info_for_step`（obs）：

| 方式 | 环境数 | 总吞吐（步/s） | 每步 act / obs（s） |
|---|---|---|---|
| 单进程 | 1 | 3.85 | 0.046 / 0.207 |
| 同进程多线程 | 2 / 4 / 8 | 3.89 / 3.67 / 3.81 | act 随线程数涨到 1.3，obs 0.4–0.7 |
| 多进程同一张卡 | 2 / 4 / 8 | 3.34 / 3.56 / 3.66 | 0.046 / 0.53、1.04、2.07 |
| 多进程分到 GPU 6、7 | 2 / 4 | 7.73 / 6.75 | 0.046 / 0.206、0.53 |
| 单进程在 learner 卡上 | GPU 0（推理） / GPU 1（更新中） | 3.72 / 2.71 | 0.045 / 0.217、0.315 |

- 训练机上复用 task 对象后，固定种子第 2、3 次 reset 各 0.7 s（改动前 27 s），第一次含专家检查 39.6 s。
- 异步 N=1 短跑（learner GPU 0–4，环境 GPU 5）：前 2 回合（update 尚未开始）83、90 步成功；update 开始后 13 回合
  1 次成功；失败回合 82–217 步结束，2 回合没抬起锤子跑满 400 步。每步约 0.41 s（obs 0.27–0.30 s，act 0.11–0.14 s）。
  每次 update 计算 8.3 s，但更新线程串行取 batch，每次 update 实际约 20 s。第 2372 步的间隔 checkpoint 由更新线程正常保存。
- 停止后以 N=4（环境在 GPU 5、6、7、0）加一步预取 `--resume` 同一运行：从第 2462 步接上（checkpoint 2372，replay 到 2461），
  4 个环境同时出回合。每环境每步 0.52 s（obs 0.33 s，act 0.15 s），总约 7.7 步/s；GPU 5–7 利用率 100%。取 batch 等待
  1.2 s，update 约每 8 s 一次。17 个回合的 buffer 文件逐个核对：只有每回合最后一步 `dones=True`，0 处错位。
  恢复后 17 回合 4 次成功。

### 2 结果分析

- **一张卡只能放一个环境。** act 不随进程数变，obs 随同卡进程数线性增长，渲染在同一张卡上排队；多线程还受 GIL 限制。
  分到不同卡后线性扩展，所以环境数受可用渲染卡数限制。推理卡上渲染不受影响，正在更新的卡上慢约 50%。
- **异步的更新速度与环境数无关。** 加预取后约每 8 s 一次 update，与同步的 7.3 s 接近。N=1 时约每回合 5 次，N=4 时约
  每回合 1.5 次（同步为 3 次）。Agent 推断：若学习速度主要取决于 update 次数，N=4 达到 90% 的墙钟时间会短于同步的
  3.2 h；若取决于每回合 update 数，N=4 反而更慢。整夜运行用来区分。
- **update 开始后成功率很低。** 两段短跑 update 后共 30 回合 5 次成功，同步运行更新后第 11–50 回合为 30/40。
  - 已排除：发布给 actor 的参数包含 π₀.₅、编码器、编辑网络与 target critic 四部分，都是 update 后的新参数。
  - Agent 推断（未验证）：同步运行是官方协议，可以重试。它第 1–10 回合成功最短 92–100 步，第 11–50 回合 30 次成功里
    25 次超过 100 步，像是第一次没打中又重试成功；第 101–200 回合 82 次成功里 61 次 ≤100 步，首次命中才回升。
    单次尝试判定把重试算失败，早期的下滑因此直接显出来。
  - 另一个差异：异步版 buffer 够一个 batch 就开始 update，同步版等 10 回合。

### 3 下一步

- 整夜运行没有跑完：N=4 有线程共享 `_last_state` 的 bug（上面 N=4 短跑的数据也受它影响），修后改为对照实验，见上一节。

## 2026-10-18 · 跨回合复用 RoboTwin task 对象：reset 从十几秒降到 1 s 以内

工程验证，不涉及算法。只跑环境端，本机 RTX 4060 Laptop（`~/.venvs/robotwin`，sapien 3.0.0b1），`beat_block_hammer`
demo_clean，训练种子段 100，单次尝试判定。代码为 expo-ft `3fbdd2d`：`RoboTwinEnv` 只建一个 task 对象，专家检查
与每次 reset 都在它上面调用 `setup_demo`，与官方评测相同。对照组在每次 reset 前换一个新 task 对象（改动前的做法）。

### 1 原始记录

| 设置 | 第 1 次 reset | 第 2 次 | 第 3 次 |
|---|---|---|---|
| 固定种子，复用 | 21.8 s | 0.5 s | 0.5 s |
| 固定种子，每次新建 | 15.6 s | 13.6 s | 13.7 s |
| 不固定种子（含专家检查），复用 | 14.7 s | 1.4 s | 1.3 s |
| 不固定种子（含专家检查），每次新建 | 14.7 s | 14.6 s | 14.5 s |

- 两种做法每次 reset 的种子（不固定时依次为 10100000、10100001、10100002）、指令都相同，reset 后的
  `observation.state` 与三路图像逐像素相同（差为 0）。
- 复用时先让左臂移动 0.3 rad、走 30 步，再 reset：状态与图像和第一次 reset 逐像素相同，动作计数归零，reset 0.4 s。
- 进程峰值内存 4.2 GB。

### 2 结果分析

- 复用后 reset 省掉的是 curobo planner 的重建：机器人与 planner 只在第一次 `setup_demo` 时建，之后走 `robot.reset`。
- 本机的绝对时间与训练机不同。训练机（h100）上同一种子、改动前的 reset 是 27 s，其中 curobo 初始化 18.3 s、新场景第一次
  取观测 7.3 s。本机改动前只要 13.6 s，不固定种子时含专家检查也只要 14.6 s，而训练机上第一次 reset 是 79.6 s。
  Agent 推断：训练机上大部分时间也花在每次新建 task 带来的 curobo 重建上（专家检查与正式回合各建一次）。训练机上的
  复用效果还没测。

### 2 结果分析

- **方法在单一场景上复现出来了。** 两个基座更新前分别是 6/10 与 1/10，更新后都升到 90% 以上：72% 基座最近 50 回合
  49/50，31% 基座 46/50。成功回合也更短（120→80 步、164→105 步）。用户结论（2026-10-18）：“RoboTwin 单任务上跑通
  EXPO-FT” Task 完成，代码通过，原算法有效。
- **较弱的基座也能拉上去，只是慢一些。** 约 7k 基座在 4–4.5 h（约 100 回合）达到 90%，15k 基座 3 h 左右首次达到，
  约 7 h（300 回合）后才稳定在 95% 以上。
- **critic 按预期收敛。** Q 的初值偏负、随更新单调回升；critic loss 很早就降到 1e-3，成功率的上升与 Q 转正的时间大致
  对应。Agent 推断：初值偏负来自 REDQ 取 2 个头的最小值，悲观偏差经折扣回溯（γ⁸≈0.92）累积。
- **π₀.₅ 参数变化很小。** 每次 update 只有 1 步 π₀.₅ BC，500 回合后参数范数只变 0.04。
  - Agent 推断：提升主要来自 critic 在候选中挑选，单独评测 RL 后的 π₀.₅ 会接近基座。未验证。
  - 用户判断：LoRA 更新仍是必要的（原文消融里不训 LoRA 成功率上不去）；这次变化小，大概率因为场景固定、没有随机性。
    若回灌到 π₀.₅ 的部分没有意义，策略就没有真正从经验中学习，更像是 π₀.₅ 去适应编辑策略、只给出大致轨迹，最后的
    成功率交给小的编辑策略。是否单独评测 π₀.₅ 留到消融或研究“吸收了多少”时再做。
- **编辑网络停在最大熵。** β=0.05、112 维时熵的上限是 112·ln 0.1 ≈ −258，默认目标 −56 达不到，温度一直上涨，熵项
  （约 300）远大于 Q（约 0.2）。Agent 推断：编辑实际上是 ±0.05 内的均匀扰动；`adjust_target_entropy=True` 会把目标改成
  −56 + 112·ln 0.05 ≈ −391。用户决定（2026-10-18）：debug 阶段超参不变，评估超参时再看。
- **证据边界。** 只有一个种子、一个任务；成功率来自训练回合，没有在评测种子段上测；每个基座只有一次运行。
- **工程。** agent checkpoint 每 2000 步存一份、每份 16 GB，参考实现最多保留 100 份，两次运行约 75 GB/h；夜里每小时
  手动删到每次运行只剩最新两份，之后 `rl_joint.sh` 改为 `--max_to_keep=2`。

### 2 结果分析

- **训练步数决定基座强弱。** 4k、约 7k、15k 依次是 14%、31%（32 回合）、72%；4k 时 loss 已降到 0.0014，loss 曲线
  不能代替成功率选步数。约 7k 落在 30% 下沿，40% 左右的基座大概需要 1 万步附近。
- **编辑动作是联合更新成功率塌陷的直接原因。** 同一批种子上，不加编辑 8/10，加 β=0.2 的编辑 0/5；RL 更新开始后
  0/10。推断：edit actor 逐步、逐维独立地在归一化关节增量上加最多 β 的偏移，β=0.2 约对应每步 ±0.1–0.15 rad
  的目标抖动；critic 未训练时约一半动作块会选中编辑过的候选，精细抓取被破坏。β=0.05 时完整策略 4/10，仍低于
  无编辑的 8/10。
- [ ] **未验证**：β=0.05 下更新能否把成功率拉回基座以上。只有更新后 2 回合，样本不足。
- **显存布局是 RL 的工程瓶颈。** GPU 0 同时放一份数据并行的训练分片和推理用参数副本；`MEM_FRACTION=0.95` 时恢复运行
  撑过了多轮 update，全新启动在第一轮就 OOM（缺约 1 GB）。
