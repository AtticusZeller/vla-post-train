# 实验记录格式契约

`docs/<method>/experiments.md` 按时间倒序累积，每个 run 一节。第一次创建文件时先写文件头
（说明三段结构、指向 `docs/<method>/` 里描述 contract 的主题文件），之后每次把新一节插在文件头
之后、上一个 run 之前。

小节标题固定为 `## YYYY-MM-DD · <config>/<exp_name> — <一句话目的>`。

---

## 三段结构

### 1 原始记录

**只放观测，不放解释。** 这一段的验收标准是：一年后有人只读这一段，能重建出这次实验跑的是什么、
结果是什么，而不被当时的结论带偏。解释一律留给第 2 段。

必含内容：

- **W&B**：完整 URL，加 project / run id / group。
- **代码版本**：method submodule 的 commit hash 与 commit title、分支；根仓库若有相关改动也记。
- **任务与权重**：任务名、各 checkpoint 路径与 step、归一化统计指纹、`precision`、`seed`。
- **收束状态**：run state（`finished` / `crashed` / `killed`）、wall time、停在第几个单位，以及
  **后续统计基于哪个子集**。run 没正常结束时必须写明原因（向用户问）。
- **影响训练的配置**：表格，按"组 / 参数 / 值"。本次相对上一次实验改动的值加粗。
  结构性、本次未调的参数不进表，但要用一句话列出它们的名字并指向权威来源（YAML / checkpoint），
  这样"没记"和"没有"不会混淆。
- **主要指标**：成功率或等价的任务指标，按有意义的分组拆开（见下面的"分组"）。
- **训练与执行观测**：时间序列指标给首尾两端的值而不是整条曲线——两端加"是否单调"足以支撑结论，
  整条曲线属于 W&B。工程健康度（NaN、fallback、丢弃、时序余量）即使全正常也要记一行，
  因为"这次是干净的"本身是下次对比的基线。

### 2 结果分析

从第 1 段的观测推结论。每个小节一个结论，标题就是结论本身而不是指标名——
写 `#### Q 平坦不是"学死了"，是 critic 在说 actor 不行`，不写 `#### Q 值分析`。

每条结论必须能追到第 1 段的具体数字。区分三种断言，不要混在一句话里：

- **观测**：直接读数或直接算出来的（成功率、相关系数、p 值）。
- **推断**：观测加上代码语义得出的（"reward 只写在最后一步，所以 3810 行里只有 48 行带信号"）。
  推断要给出代码位置，读者才能自己复核。
- **猜想**：解释性的、还没有证据分开的。用 `- [ ] **未验证**：…` 标注，并**写清怎么验证**。

用户在讨论里提出的判断要保留并标明出处（`**（用户提出）**`），包括还没验证的。这是记录不是论文，
研究者当时怎么想的，下次读的时候有用。

### 3 下一步

未确认的候选调整，按"最可能解释第 2 段现象"排序，不按改动成本。

每条给出：改什么、支持它的证据、**观测判据**（跑完之后看哪个指标的什么变化算这条成立或被否），
以及已知风险。没有观测判据的条目等于没写——下一轮无法判断它对不对。

`- [ ]` 表示尚未验证或尚未执行。这些条目经用户确认后才搬进 `plan.md` 成为事务；
`docs/AGENTS.md` 规定 `plan.md` 只放已确认、未完成的工作，所以不要提前搬。

结尾用 `#### 暂不处理` 收掉本轮明确不动的现象，每条一句话说明为什么不动。
没有这一节的话，下一轮会重新发现同样的问题并重新讨论一遍。

## 分组：主要指标必须先排除混淆

单一的成功率/回报数字几乎总是被别的东西污染过。写进第 1 段之前，先问日志里还有什么能独立解释它：
人工接管、自动重试、提前截断、课程难度变化、评估集和训练集重叠。

把主要指标按这些因素拆开，各组都列出来，并在第 2 段说明哪一组才是要比的那个。
拆开之后每组的 n 通常会变得很小，所以 n 和显著性检验要一起给——
`14/29 = 48.3%，Fisher p=1.0` 是可用的，`48.3%` 单独放着会被当成结论。
